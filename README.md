# 빌드브리프 · BuildBrief

**아이디어를 다른 사람과 함께 검토할 수 있는 서비스 기획 초안으로 정리합니다.**

아이디어만 있는 사람도 문제와 사용자부터 기능, 이용 과정, 화면까지 하나씩 구체화할 수 있는 기획 도구입니다. 개발 경험이 없어도 익숙한 말과 선택지로 시작하고, 선택한 이유와 아직 모르는 점을 함께 남길 수 있습니다.

[서비스 이용](https://buildbrief.moon0sik.cloud/) · [변경 내역·최신 버전](https://github.com/YoungsikMoon/buildbrief/releases) · [오류·개선 제안](https://github.com/YoungsikMoon/buildbrief/issues/new) · [개발자 LinkedIn](https://www.linkedin.com/in/moonyoungsik95)

## 무엇을 만들 수 있나요?

1차 목표는 **아이디어를 구체화하는 데 필요한 정보를 정리하는 것**입니다. 필요한 기능과 화면을 연결하고, 처음 만들 범위와 확인할 일을 담은 기획 초안을 만듭니다. 이 초안을 사람 또는 AI와 함께 검토하며 요구사항을 보완할 수 있습니다.

| 결과물 | 담기는 내용 | 사용하는 방법 |
| --- | --- | --- |
| 서비스 기획 초안 | 입력한 답변, 기능·화면 연결, 선택 이유, 미정 사항 | 화면에서 확인하거나 Markdown 파일로 내려받기 |
| AI에게 전달할 요청문 | 기획 초안과 보완 지침, 비교·추천을 요청한 질문 | ‘AI와 기획 다듬기 · 복사’ 후 원하는 AI 대화에 붙여 넣기 |
| 프로젝트 백업 | 답변·메모·추천 요청·작성 단계 등 프로젝트 기록 | JSON 파일로 보관하고 ‘백업 불러오기’로 불러오기 |

사이트에서 AI를 자동 실행하거나 코드를 생성하지 않습니다. 기술 스택도 자동 확정하지 않습니다. AI 전달문은 바로 개발하기보다 빠진 정보와 모순을 확인하고 기획을 보완하도록 안내합니다. 브라우저에서 복사가 허용되지 않으면 요청문을 Markdown 파일로 내려받습니다.

## 10단계 작성 흐름

순서대로 작성하거나 왼쪽 목차에서 필요한 단계로 이동할 수 있습니다. 모든 질문을 한 번에 채울 필요는 없습니다.

| 단계 | 주제 | 정리하는 내용 |
| --- | --- | --- |
| 01 | 아이디어 소개 | 프로젝트 이름, 누구에게 무엇을 제공할지 |
| 02 | 문제와 기존 방법 | 불편한 상황, 현재 해결 방식, 바라는 변화 |
| 03 | 사용할 사람과 환경 | 첫 사용자, 이용 목적과 상황, 기기와 이용 방식 |
| 04 | 필요한 기능 | 기능 후보, 기능별 사용자·기대 결과·우선순위 |
| 05 | 대표 이용 과정 | 시작부터 결과까지의 순서, 예외·실패 시 경험 |
| 06 | 로그인과 사용자 구분 | 로그인 범위와 방법, 가입 조건, 계정 관리, 역할별 권한 |
| 07 | 자료와 서비스 규칙 | 보관할 자료와 접근 범위, 선택한 기능에 필요한 규칙 |
| 08 | 참고 서비스와 디자인 방향 | 참고 URL과 참고할 부분, 화면 분위기, 기존 브랜드 자료 |
| 09 | 화면 구성 | 화면 목적, 연결할 기능, UI 요소, 빈 화면·오류·모바일 경험 |
| 10 | 첫 버전 정리 | 기능별 출시 범위 검토, 제외할 일, 아이디어 검증과 남은 질문 |

예약·결제·파일·위치·AI 등의 후속 질문은 관련 기능이나 답변을 선택했을 때 나타납니다. 조건이 바뀌어 숨겨진 답변은 보관하되 현재 기획 초안에서는 제외합니다.

## 주요 기능

- **기능을 구체화하는 카드**: 검색, 예약, 알림, 결제 등 후보에서 필요한 기능을 추가하거나 직접 만듭니다. 같은 유형의 기능을 여러 개 만들고 실제 이름·사용자·기대 결과를 적을 수 있습니다.
- **기능과 화면 연결**: 대표 이용 순서와 화면에 앞서 만든 기능을 연결합니다. 상단 바, 사이드바, 목록, 카드, 표, 달력, FAB 등 화면 요소를 작은 그림과 도움말로 살펴보고 함께 선택합니다. 작은 그림은 요소를 설명하는 예시이며 화면 배치를 확정한 결과물은 아닙니다.
- **서비스에 맞는 로그인 계획**: 자체 이메일·아이디 로그인, 인증 링크·번호, 카카오·네이버·Google·Apple 등을 비교합니다. 빌드브리프 자체에 로그인하는 기능이 아니라, 만들 서비스의 로그인 방식을 정리하는 질문입니다.
- **참고 자료 정리**: URL을 한 줄씩 추가하거나 여러 줄로 붙여 넣고 참고할 부분을 기록합니다. 주소를 입력해도 사이트 내용을 자동으로 열람하거나 분석하지 않습니다.
- **답변·선택 이유 기록**: 질문 아래 펼침 영역의 빈 입력란에 판단 근거를 자유롭게 남깁니다. 답변과 별도로 자동 저장되며 기획 초안과 백업에도 포함됩니다.
- **질문에 맞는 추천 요청과 직접 입력**: 대안을 비교할 수 있는 질문에만 ‘AI에 추천 요청’을 제공합니다. 목록 밖 답변이 가능한 질문은 ‘직접 입력’을 선택하면 후속 입력란이 나타납니다. 추천 요청은 기존 답변을 지우지 않고 AI 전달문에 함께 담깁니다.
- **여러 프로젝트 관리**: 같은 브라우저에서 프로젝트를 만들고 전환하며 이름 변경, 개별·전체 백업, 백업 가져오기를 할 수 있습니다. 프로젝트별 답변과 작성 위치를 따로 보관합니다.
- **PC·모바일 작성 환경**: PC에서는 사이드바로, 모바일에서는 ‘프로젝트·목차’ 버튼으로 단계를 이동합니다. 백업 내려받기·백업 불러오기·기획 초안은 PC 상단과 모바일 하단 고정 영역에서 바로 실행합니다. 브라우저 저장 상태는 모바일에서도 상단에 글자로 표시하며 눌러 저장 안내를 볼 수 있습니다.

## 진행률은 어떻게 계산하나요?

사이드바에 전체 **작성 진행률(%)과 막대**, `질문 25개 중 3개 작성` 형태의 요약을 표시합니다. 각 대항목 옆의 `1/4`는 **작성한 질문 1개 / 현재 해당하는 질문 4개**라는 뜻입니다. 모바일 상단에서도 진행률을 확인할 수 있습니다.

- 10단계 전체에서 현재 답변 조건에 해당하는 질문만 셉니다. 후속 질문이 나타나거나 숨겨지면 전체 수와 대항목별 수가 함께 바뀝니다. 질문이 늘면 작성 중에도 비율이 내려갈 수 있습니다.
- 답변이 있는 질문을 세며, 일반 선택 질문에서 직접 고른 ‘아직 미정’도 기록한 답변으로 봅니다. 기능·화면 같은 반복 목록은 카드 수와 관계없이 질문 하나입니다.
- 목록의 일부 내용만 입력해도 작성한 질문으로 셉니다. 기능 후보를 추가하면 기본 이름이 들어가므로 기능 질문이 작성된 것으로 계산됩니다. 반면 빈 카드나 기능 카드의 자동 ‘아직 미정’ 우선순위만으로는 작성 수가 늘지 않습니다.
- 첫 버전의 기능 우선순위 검토는 기능을 하나 이상 추가하고 모든 기능을 ‘첫 버전에 필요’ 또는 ‘나중에’로 정했을 때 반영합니다.
- 선택 이유 메모나 AI 추천 요청만 남긴 경우는 작성 수에 더하지 않습니다. 조건에서 숨겨진 질문도 계산에서 제외합니다.

진행률은 **입력 현황**입니다. 100%가 기획의 완성도나 개발 준비 완료를 뜻하지는 않습니다. 답변을 바꾸거나 새로고침하면 저장된 프로젝트를 기준으로 다시 계산합니다.

## 저장과 백업

답변은 서버에 전송하지 않고 **현재 브라우저의 localStorage**에 자동 저장합니다. 같은 기기·브라우저·프로필·사이트 주소에서 다시 열면 이어서 작성할 수 있습니다. 일반 모드에서 정상 저장되었다면 새로고침이나 PC 재부팅만으로 지워지지는 않습니다.

- ‘이 브라우저에 저장됨’을 누르면 저장 상태와 보관·복구 방법을 확인할 수 있습니다.
- ‘백업 내려받기’는 현재 프로젝트를, ‘관리’의 ‘전체 프로젝트 백업’은 모든 프로젝트를 JSON 파일로 내려받습니다.
- ‘백업 불러오기’는 파일을 검증한 뒤 새 프로젝트로 추가합니다. 현재 프로젝트를 덮어쓰지 않습니다.
- 저장 실패, 기존 자료 읽기 실패, 다른 탭의 변경을 감지하면 안내합니다. 충돌 시 덮어쓰기를 막으며, 현재 입력은 백업한 뒤 저장 안내를 따라 복구할 수 있습니다.

사이트 데이터 삭제, 시크릿 모드 종료, 브라우저 초기화, 기기 고장 등에 대비해 중요한 기록은 파일로 백업하세요. 다른 브라우저·기기·사이트 주소로 자동 동기화되지 않습니다. 브라우저 저장과 백업 파일을 별도로 암호화하지 않으므로 실제 비밀번호나 API 키를 입력하지 마세요. 외부 AI에 초안을 붙여 넣는 경우에는 전달할 내용을 직접 확인하세요.

현재 저장 키는 `buildbrief.ideas.v1`이며 백업 형식은 단일 프로젝트 `buildbrief-idea`, 전체 프로젝트 `buildbrief-ideas`입니다. 이전 기술 설계 질문지의 저장 키는 삭제하지 않지만, 이전 모델의 답변·백업을 현재 아이디어 기획 모델로 자동 변환하지는 않습니다.

## 로컬 실행

HTML·CSS·JavaScript로 만든 정적 사이트입니다. 앱 실행에 백엔드, 데이터베이스, AI API 키, npm 패키지 설치가 필요하지 않습니다. 아래 예시는 Git과 Python 3을 사용합니다.

```sh
git clone https://github.com/YoungsikMoon/buildbrief.git
cd buildbrief
python -m http.server 4173 --bind 127.0.0.1 --directory dist
```

브라우저에서 [http://127.0.0.1:4173/](http://127.0.0.1:4173/)을 엽니다. 서버는 실행한 터미널을 유지하며, 종료할 때는 `Ctrl+C`를 누릅니다. 개발 서버에서는 Cloudflare의 `_headers` 설정이 적용되지 않습니다.

## 수정과 검증

검증에는 Node.js를 사용하며 GitHub Actions와 Pages 빌드는 **Node.js 24**로 설정되어 있습니다. 로컬 서버와 별도의 터미널에서 저장소 루트를 열고 실행하세요.

```sh
node check.cjs
node scripts/release.cjs --test
node scripts/build.cjs --test
```

질문 표시 조건, 진행률, 기능·화면 연결, 로그인 조합, 보고서 출력, 입력 검증, 프로젝트 분리, 백업 호환성, 버전 발급과 배포 버전 표시를 검사합니다. 브라우저에서는 수정한 입력 흐름과 PC·모바일 화면도 확인하세요.

JS·CSS를 수정하면 `dist/index.html`의 해당 `?v=` 값도 갱신해야 합니다. 값은 파일의 줄바꿈을 LF로 맞춘 내용의 **SHA-256 앞 12자리**이며 `check.cjs`가 일치 여부를 검사합니다. 전체 로컬 빌드 검증은 `node scripts/build.cjs`로 실행할 수 있습니다. 이 명령은 위 검사를 실행하고 HTML의 앱 버전 표시를 `개발 버전`으로 설정합니다.

| 파일 | 역할 |
| --- | --- |
| `dist/index.html` | 페이지 구조, 대화 상자, 자산 참조와 버전 표시 영역 |
| `dist/questions.js` | 10단계 질문, 표시 조건, 기능 후보, 화면 요소 |
| `dist/guides.js` | 선택지별 도움말 |
| `dist/app.js` | 입력 편집기, 진행률 표시, 자동 저장, 프로젝트 관리, 내보내기 |
| `dist/report.js` | 입력 검증, 조건과 진행률 계산, 기획 초안·AI 전달문 |
| `dist/projects.js` | 프로젝트 저장·백업 형식과 가져오기 검증 |
| `dist/styles.css` | PC·모바일 레이아웃 |
| `dist/_headers` | Cloudflare Pages의 보안·캐시 응답 헤더 |
| `check.cjs` | 앱 회귀 검사와 자산 해시 검사 |
| `scripts/release.cjs` | 날짜별 Git 태그와 GitHub Release 발급 |
| `scripts/build.cjs` | 빌드 검증과 배포 커밋의 앱 버전 표시 |
| `.github/workflows/release.yml` | Pull Request·main 검증과 자동 릴리스 |
| `wrangler.jsonc` | Pages 프로젝트 이름과 공개 디렉터리 설정 |

## 버전 관리

버전 형식은 **`yymmdd.01`부터 `yymmdd.99`까지**입니다. Git 태그와 GitHub Release가 버전의 기준이며, 발급 날짜는 **한국 시간(Asia/Seoul)**을 사용합니다. 최신 버전은 [Releases](https://github.com/YoungsikMoon/buildbrief/releases)에서 확인하세요.

- Pull Request는 검증만 진행합니다. `main`에 변경을 푸시하거나 병합하면 검증 성공 후 자동으로 릴리스를 발급합니다. 문서만 수정한 커밋에도 같은 규칙이 적용됩니다.
- 같은 날에는 `260922.01` → `260922.02`처럼 증가하고, 다음 날짜의 첫 발급은 `260923.01`입니다.
- 같은 커밋을 재실행하면 기존 버전을 재사용합니다. 테스트 실패 시 새 버전을 발급하지 않습니다.
- 하루 99개를 넘으면 중단합니다. 기존 태그를 덮어쓰거나 이동하지 않습니다. 변경 없는 날짜에는 버전을 만들지 않습니다.
- 릴리스 작업은 대기열에서 순서대로 실행하며, 필요한 경우 Actions에서 `main`을 대상으로 수동 실행할 수 있습니다.

공개 앱 상단에는 **실제 배포 커밋의 버전**이 표시되며 누르면 해당 릴리스를 엽니다. 로컬에서는 `개발 버전`으로 표시합니다. Pages 미리보기도 일치하는 태그가 없으면 개발 버전을 사용합니다.

## Cloudflare Pages 배포

현재 서비스는 Cloudflare Pages에서 **`dist`의 정적 파일만** 제공합니다. GitHub 저장소 연동으로 배포하며 별도 배포 API 토큰은 필요하지 않습니다.

| 설정 | 값 |
| --- | --- |
| 프로젝트 이름 | `buildbrief` |
| Production branch | `main` |
| Root directory | 저장소 루트 |
| Framework preset | 없음 |
| Build command | `node scripts/build.cjs` |
| Build output directory | `dist` |
| 빌드 환경 변수 | `NODE_VERSION=24` |

`main` 변경 후 GitHub 릴리스와 Pages 빌드가 각각 시작됩니다. 운영 빌드는 체크아웃한 커밋과 `CF_PAGES_COMMIT_SHA`가 일치하는지 확인하고, 그 커밋의 원격 릴리스 태그를 최대 5분 기다려 버전을 표시합니다. 태그를 찾지 못하거나 여러 버전이 같은 커밋을 가리키면 실패합니다. 릴리스 발급이 늦어 실패한 경우에는 릴리스 성공 후 Pages 빌드를 다시 실행하세요.

배포 디렉터리는 `dist`를 유지하세요. `dist/_headers`에는 스크립트 출처 제한, 스크립트의 외부 통신 차단(`connect-src 'none'`), 외부 사이트의 프레임 삽입 차단 등의 설정이 있습니다. 클라우드 배포 자체가 답변의 서버 저장이나 기기 간 동기화를 추가하지는 않습니다.

2026-09-23 확인 기준, Functions를 호출하지 않는 정적 파일 요청은 [무료·무제한](https://developers.cloudflare.com/pages/functions/pricing/#static-asset-requests)이며 Free 플랜은 [월 500회 빌드](https://developers.cloudflare.com/pages/platform/limits/#builds)를 지원합니다. 새로 배포하거나 서버 기능을 추가할 때는 공식 요금·한도를 다시 확인하세요.
